# Обновления и откаты

Окно **Справка → Проверить обновления...** управляет тремя компонентами, каждым отдельно или всеми вместе (`src/update/mod.rs`, окно — `src/app/updates.rs`):

| Компонент | Что это | Источник | Чем ставится |
|---|---|---|---|
| Native | оригинальный клиент AmneziaWG (режим 1) | релизы GitHub клиента AmneziaWG для Windows (`src/update/feed.rs`, `NATIVE_REPO`) | `msiexec` (`src/update/native.rs`) |
| Engine | встроенный движок режима 2: `tunnel.dll` и `wintun.dll` | релизы этого проекта, подписанный манифест | замена набора файлов (`src/update/ours/`) |
| App | сама программа, `awg-ui.exe` | релизы этого проекта, подписанный манифест | замена набора файлов, затем перезапуск ядра |

Когда обновляются все сразу, порядок такой: Native, Engine, App (`ORDER`): программа последняя, потому что она перезапускает ядро.

## Где это работает

1. Менеджер обновлений (`src/update/manager.rs`) живёт в **агенте** (`src/daemon/agent/updates.rs`), а не в ядре и не в окне. Окно шлёт `Updates(UpdateOp)` в
   канал агента; ядро окну прежней версии на `Updates` отвечает отказом с объяснением. См. [Протоколы](protocols.ru.md).
2. Туннелей менеджер касается только тремя внутренними запросами к ядру, `HoldNative`, `Release` и `ReconnectEngine` (`src/update/core_link/`); см. [Надзор](supervisor.ru.md).
3. Одна работа за раз (проверка, обновление или возврат); вторая команда во время работы получает «занято». Работа идёт в своём потоке, окно видит её ход
   (`busy`) в состоянии. Паника внутри работы — событие в журнале, а не остановка процесса.
4. Сеть: HTTPS через WinHTTP (`src/update/net.rs`), системный прокси, перенаправления никогда не понижаются до HTTP, сетевые таймауты по 30 с, общий срок 2 мин
   на малый запрос и 30 мин на загрузку. Пределы: ответ API GitHub 2 МиБ, текст релиза обрезается до 2000 символов, манифест 64 КиБ, MSI 64 МиБ, файл нашего
   релиза не более 256 МиБ и не более размера из манифеста.
5. Данные — в `C:\ProgramData\AmneziaWG UI Dark\updates`: `history.json`, `state.json` (итог последней проверки), `backups\`, `downloads\` (временное, чистится
   после каждой работы и при запуске), `logs\` (журналы `msiexec`), `started.json` (идёт возврат AmneziaWG), `after_change.json` (переподключение движка, ещё не принятое ядром), `app\` (новая сборка для окна).

## Что делает команда

1. `State` — текущее состояние, без сети.
2. `Check` — опрашивает источники: последний релиз клиента AmneziaWG, последний релиз этого проекта с манифестом, а для строки движка — новейшую стабильную метку
   репозитория движка Amnezia (показывается как «актуален», «есть новее — придёт с обновлением программы» или «не проверялось»). Итог попадает в
   `state.json`; ошибка источника видна только в его строке. Релиз этого проекта без подписанного манифеста (до 0.4.0) — не ошибка: его ставят только вручную, окно
   сообщает об этом нейтрально.
3. `Apply(список)` — сначала свежая проверка, затем для каждого выбранного компонента в порядке `ORDER`:
   1. найденная версия должна совпасть с версией, которую подтвердил пользователь (иначе компонент не трогается, в истории строка с ошибкой);
   2. она должна быть новее установленной (числовое сравнение по частям через точку, ведущая `v` не учитывается); нет — только запись в журнал;
   3. **резервная копия текущей версии** (см. ниже); не вышла копия — компонент пропускается;
   4. установка; строка истории `Update` с `from`, `to` и ссылкой на копию, сделанную прямо перед ней (`prior_backup`);
   5. при успехе — событие в журнале; для движка ядро просят переподключить туннели режима 2 (`ReconnectEngine`). Этот запрос — долг на диске:
      `after_change.json` отмечает движок до замены файлов и очищается только после того, как ядро приняло запрос (или замена вернулась с
      ошибкой). Отметку, оставшуюся от погибшего агента или от неответившего ядра, менеджер повторяет на ближайшем такте планировщика (раз в 30 с,
      не во время работы); неудачный повтор пишется в журнал один раз до успеха.
   Сбой одного компонента остальные не останавливает.
   Тот же запрос без окна, для проверки живого обновления сценарием: `awg-ui.exe --core-updates apply native|engine|app <версия>`
   (`parse_cli` в `src/update/mod.rs`). Он уходит агенту так же, как по кнопке «Обновить» окна, с теми же проверками; команда ждёт до
   10 минут, пока идёт работа (для `check` — 2 минуты), и печатает состояние и последние строки истории.
4. `Restore(строка)` — см. [Откат](#откат).

## Проверка

Пока не прошла каждая проверка ниже, ничего не ставится.

1. **Оригинальный AmneziaWG (MSI)** (`src/update/backup.rs`, `src/update/native.rs`):
   1. в релизе должна быть сумма SHA-256 файла (поле `digest` ассета GitHub); нет суммы — отказ; размер и SHA-256 загрузки должны совпасть;
   2. подпись Authenticode проверяет Windows (`WinVerifyTrust`, отзыв проверяется по всей цепочке, без окон);
   3. имя сертификата подписавшего должно быть в точности `Privacy Technologies OU` (`PUBLISHER`);
   4. таблица `Property` самого MSI читается без установки: `UpgradeCode` должен быть `{876B57E4-4490-4442-A983-721EE141B00D}` (продукт amd64), а `ProductVersion` —
      той версией, которую просили.
   Те же проверки идут над сохранённым установщиком копии **до** того, как при возврате что-либо удаляется.
2. **Наши движок и программа: подписанный манифест** (`src/update/sign.rs`):
   1. в релизе есть `update-manifest.json` и `update-manifest.json.sig`;
   2. подпись — **SSHSIG** (`-----BEGIN SSH SIGNATURE-----`), сделана `ssh-keygen -Y sign`, алгоритм **Ed25519**, пространство имён **`awg-ui-update`**.
      Проверка требует: SSHSIG версии 1, пространство имён ровно эта строка, ключ подписи равен открытому ключу, вшитому в программу (`UPDATE_KEY`), хеш
      сообщения `sha512` или `sha256` и верную подпись Ed25519 над точными байтами JSON;
   3. затем манифест проверяется по полям: версии — 1–64 символа из букв, цифр, `.`, `-`; запись программы — `awg-ui.exe`; имена файлов — простые имена; каждая
      SHA-256 — 64 строчных hex-цифры; файлы движка — ровно `tunnel.dll` и `wintun.dll`;
   4. каждый файл скачивается с пределом размера, его размер и SHA-256 сверяются с записью манифеста;
   5. при установке манифест скачивается **заново** и должен совпасть целиком с тем, что проверен при поиске (переподписанный релиз с теми же версиями, но другими
      суммами иначе оставил бы поставленные файлы, не соответствующие манифесту). Ставятся именно скачанные байты, потому что подпись покрывает их точно.
3. **Доверие к движку во время работы** (`src/engine.rs`, `verify`): `tunnel.dll` или `wintun.dll` загружается, только если его SHA-256 равна сумме, вшитой в
   программу при сборке, или указана в проверенном локальном манифесте в папке программы (его кладёт обновление движка).
4. **Обновление самого окна** берёт `awg-ui.exe` из папки, которую выкладывает агент (`updates\app`), проверяет подпись манифеста вшитым ключом, версию манифеста
   (равна версии ядра), размер и SHA-256 файла; ставятся проверенные байты (файл второй раз не читается).

## Резервные копии и история

1. Перед каждым обновлением и каждым возвратом текущая версия копируется в `updates\backups\<строка>-<компонент>-<версия>\` с файлом `component.json`:
   1. Native: `installer.msi` (скачивается заново из релиза установленной версии и проверяется, как выше) и `configs\` — файлы туннелей `*.conf.dpapi`, копируются как
      непрозрачные файлы, не расшифровываются; ссылки и прочие точки повторной обработки пропускаются;
   2. Engine: обе DLL и локальный манифест, если он есть;
   3. App: набор файлов сборки и её версия.
2. История (`history.json`, пишется через временный файл — оборванная запись её не портит) состоит из строк `Backup`, `Update` и `Restore` с `from`, `to`, успехом,
   текстом ошибки и `prior_backup`. Испорченный файл попадает в журнал событий, история начинается пустой; строки с недопустимыми сочетаниями полей исправляются, каждое
   исправление пишется в журнал.
3. Пределы действуют после каждой работы и при запуске: не больше 200 строк, не больше 5 копий на компонент (первыми уходят старые по номеру строки, **кроме**
   копии, сделанной перед последним обновлением или возвратом этого компонента, — она не удаляется никогда), не больше 20 журналов `msiexec`. Папки копий отброшенных
   строк удаляются.
4. Кнопка **Вернуть** строки ведёт (`src/update/restore_target.rs`; одно правило для окна и для команды):
   1. строка `Backup` — к своей копии;
   2. строка `Update` — к копии, сделанной прямо перед обновлением (версия «было»);
   3. строка `Restore` — к копии версии, которую этот возврат заменил.
   Недоступна, если версия цели уже установлена или её копии на диске больше нет.

## Откат

1. **Нужен UAC.** `Restore` принимается только от клиента, у которого токен повышен и группа «Администраторы» действует (`updates_allowed`; агент проверяет это при
   каждом возврате, а не только при возврате к более старой версии: версии сравнимы не всегда, а простое правило нечем обойти). Окно запускает помощник
   `awg-ui.exe --core-updates restore <строка>` с правами администратора (запрос UAC); он отправляет запрос агенту и выходит, ход виден в окне. `Restore` без
   повышения получает ошибку, а в журнале событий остаётся предупреждение с учётной записью вызвавшего. Иначе любая программа владельца молча откатила бы компонент
   к версии с известными дырами. `Check` и `Apply` повышения не требуют.
2. Возврат сначала копирует **текущее** состояние (чтобы можно было вернуться обратно), затем ставит из выбранной копии; строка хранит `prior_backup`.
3. Возврат **Native**: сохранённый установщик проверяется (подпись, `UpgradeCode`, `ProductVersion` равна версии копии) до того, как что-либо удалено; туннели
   сливаются (текущий набор главнее, файлы, которые есть только в старой копии, добавляются); текущая версия удаляется, старая ставится, туннели возвращаются. Старая
   версия не встала — снова ставится копия, сделанная перед возвратом, вместе с её туннелями (сообщение говорит «возвращено прежнее» или «возврат не удался» с путём к
   копии). Строка истории пишется **до** работы, с файлом-отметкой; если процесс остановился посередине, при следующем запуске строка становится ошибкой «прервано».
4. Пока MSI работает, ядро снимает туннели режима 1 с надзора (`HoldNative`, аренда на 15 минут; работающие и желаемые ядро выбирает само) и возвращает
   потом (`Release`) при любом исходе; ядро недоступно или аренду взять не удалось — MSI не запускается.
5. MSI закрывает окно AmneziaWG (процесс `amneziawg.exe` в сеансе пользователя) в самом начале, и AmneziaWG сам его не открывает. Ядро и агент
   работают от SYSTEM в сеансе 0 и окон не запускают, поэтому окно AmneziaWG открывает снова **окно этой программы** (`src/app/native_reopen.rs`):
   1. Агент — сторона, которая запускает MSI, — прямо перед ним (перед установкой, а при возврате — перед удалением) смотрит, работает ли процесс
      `amneziawg.exe` в каком-нибудь сеансе, кроме 0 (`update::native::ui_open`, только список процессов с номерами сеансов; в сеансе 0 — его службы).
      MSI целиком идёт 1–3 с, окно с опросом раз в секунду не застало бы ни работу, ни открытое окно AmneziaWG.
   2. В конце работы (успех или ошибка) агент записывает в `state.json` `NativeUiMark { seq, was_open }`: `seq` растёт на единицу с каждой работой,
      где был MSI. В `State` агента это поле `native_ui`; окно читает его раз в секунду, и скрытое в трее тоже.
   3. Окно решает один раз на каждый новый `seq`, даже если самой работы не видело: `was_open`, процесс AmneziaWG в его сеансе не вернулся сам и
      AmneziaWG установлен — оно просит агента `NativeOp::Reopen`: тот же запуск, что пункт меню **Окно AmneziaWG**, но в любом режиме
      (возвращается то, что у пользователя было открыто, и в режиме 2). Сбой — в журнал событий.
   4. Не открывается: окно AmneziaWG было закрыто до MSI; первый `seq`, который окно видит после своего запуска (прошлая работа); окна программы нет
      вовсе. Отметку агента, которого сразу после работы перезапустило обновление программы, окно всё равно увидит.

## Установка движка и программы

1. **Замена набора файлов** (`src/update/ours/fileset.rs`): каждый заменяемый файл переименовывается в `<имя>.old-<random>` (загруженную DLL и работающий exe переименовать
   можно), новый копируется на его место. Любая ошибка — всё поставленное убирается, всё отодвинутое возвращается; не вернувшийся файл переименовывается в
   `<имя>.keep-<random>` и называется в ошибке (файлы `.keep-` никогда не удаляются). Оставшиеся `.old-` убираются при следующей установке и при запуске службы.
2. **Обновление программы**: новый `awg-ui.exe` проверяется и ставится в папку программы; если стоящие DLL движка не совпадают с новым манифестом, они скачиваются и ставятся
   тем же набором; манифест и подпись ставятся всегда. Сборка выкладывается и окну (`updates\app`, чтение для учётной записи владельца), затем отдельный помощник
   `awg-ui.exe --restart-core <заменённый набор>` запускается вне объекта задания агента (агент гибнет вместе с ядром, которое перезапускает). Не удалось выложить
   или запустить помощник — набор откатывается, ядро остаётся на прежней сборке.

## Самообновление и возврат при `--restart-core`

`src/update/ours/fallback.rs`. Помощник работает только от SYSTEM (иначе код выхода 2).

1. Через 2 с он останавливает службу ядра (ждёт до 30 с) и запускает снова: до 4 попыток с паузой 5 с, каждая ждёт состояния «работает» до 30 с; ядро сообщает его, только
   когда его собственный канал ответил на `Hello` той же версией.
2. Если имя канала занято другой программой, новая сборка не виновата (иначе любая программа владельца откатывала бы обновление без UAC): делается до 8 кругов
   запуска, около 10 минут; имя не освободилось — ядро остаётся остановленным на новой сборке, его поднимет действие диспетчера служб при сбое или перезагрузка (код 10).
3. Новое ядро не поднялось: остановить его, **вернуть весь заменённый набор** и запустить прежнюю сборку. Порядок: сначала новый подписанный манифест уходит в сторону, затем
   по одному DLL и exe, затем возвращается прежний манифест — смешанный набор не считается доверенным ни на одном шаге, даже при обрыве. В историю попадает строка
   `Update` с ошибкой и строка `Restore` от новой версии к прежней, в журнал ядра — исход. Коды выхода: 0 новое ядро работает; 2 не SYSTEM; 3, 4 нет доступа к
   службе; 5 служба не остановилась; 6 возвращена прежняя сборка и работает; 7 возвращать нечего; 8 возвращено не всё (ядро не запускается, набор смешанный); 9 прежняя
   возвращена, но не запустилась; 10 имя канала так и не освободилось.
4. **Окно** обновляет себя при следующем запуске: если в папке `updates\app` лежит сборка той же версии, что у ядра, новее своей, и она проходит проверки манифеста
   выше, окно отодвигает свой `awg-ui.exe` в `awg-ui.exe.old`, пишет на его место проверенные байты и запускает новый процесс с теми же аргументами и переменной
   `AWG_UI_UPDATED_FROM=<pid>`. Новый процесс ждёт выхода старого до 10 с (тот держит мьютекс единственного экземпляра) и удаляет `.old`. Не записалось — старый exe
   возвращается на место.

## Ежедневная проверка и напоминание

1. **Проверка** (агент, `src/update/clock.rs`, `Manager::daily`): поток просыпается каждые 30 с. Первая проверка — через 120 с после запуска агента; дальше — когда прошли 24 ч
   с последней, записанной в `state.json`, или проверок ещё не было. Часы ушли назад — «не пора». Идёт другая работа — шаг пропускается. Проверка только **смотрит**:
   без пользователя ничего не ставится. О каждой новой версии в журнал событий идёт одна строка (`announced` в `state.json`).
2. **Напоминание** (окно, `src/app/reminder.rs`):
   1. новая версия сообщается сразу; уже сообщённая и всё ещё не установленная — раз в сутки (`REMIND_EVERY` = 24 ч);
   2. только если пользователь за компьютером (ввод за последние 5 минут) и Windows принимает уведомления (нет полноэкранной программы, презентации, «не беспокоить»
      и заблокированного сеанса); иначе проверка повторяется через 3 минуты. Windows не ответила — считается, что пользователь на месте;
   3. уведомление появляется справа внизу окна (**Открыть** / **Позже**; **Позже**, крестик и `Esc` откладывают следующее напоминание на сутки); если окно спрятано в
      трей, Windows показывает ещё и уведомление;
   4. после установки список предложенного пустеет, напоминания прекращаются. О чём уже сообщали и когда напоминали в последний раз, хранится в настройках окна.
3. Отметка на меню **Справка** ставится, когда найдено обновление, независимо от напоминания.
